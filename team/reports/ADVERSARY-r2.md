### Находка 1 (главная). `arb-scan` не читает объявленный `size_unit`. На OKX это 100×

**Тесты:** `crates/arb-adversary/tests/scan_declared_unit.rs` — три падающих,
один проходящий (доказательство, не находка).

| Тест | Что утверждает | Падает |
|---|---|---|
| `okx_long_reports_a_notional_one_hundred_times_the_position_it_opens` | `Opportunity::notional` = 1 000, код даёт 100 000 | да |
| `okx_short_reports_a_leg_margin_one_hundred_times_the_capital_at_risk` | `OppLeg::margin` = 999.9875, код даёт 99 998.75 | да |
| `one_size_for_two_units_leaves_the_position_naked` | базовая экспозиция ног равна; расходится на 1.2375 BTC | да |
| `the_hundredfold_row_is_not_blocked_by_anything` | строка **не заблокирована** и ранжируема | нет, проходит |

**Нарушенное правило.** `decisions/024` п. 2, дословно: «Вывод единицы из
`contract_size` запрещён.» `SizeUnit::implied_by` разрешён только для сверки
объявленного с подразумеваемым, не вместо него.

**Где именно.** `crates/arb-scan/src/scan.rs` ветвится по `spec.size` в обоих
местах, где размер встречается с ценой:

```
requested_in_book_units:  ContractSize::BasePerContract(_) => target.div_price(..)
notional_of:              ContractSize::BasePerContract(_) => size.mul_price(..)
```

`BasePerContract(_) => Base` — это ровно тело `SizeUnit::implied_by`
(`arb-types/src/instrument.rs:116`). То есть обе функции читают подразумеваемую
единицу.

**Проверено грепом по всему воркспейсу:** `spec.size_unit` потребляется в
**одном** месте — `crates/arb-engine/src/live.rs:401`, где он **печатается**
(`writeln!`, блок начинается на 396). Арифметика не читает его нигде. То есть
`decisions/024` завёл обязательное объявленное поле, и ни одно число от него не
зависит.

**Почему это деньги именно сейчас, а не в раунде 1.** Все фикстуры объявляют
`size_unit = "base"`, и собственный хелпер тестов `arb-scan` прошивает
`size_unit: SizeUnit::Base` в каждом спеке, который строит (`scan.rs:736`, с
комментарием «Every spec these tests build is linear or spot, and `arb-scan`
works in ladder units throughout»). Комментарий склеивает два разных
утверждения: что сканер работает в единицах лестницы (верно), и что у
**линейного** инструмента лестница в базе (неверно).

Адаптер OKX раунда 2 — первый инструмент в воркспейсе, где объявленное и
подразумеваемое расходятся. `crates/arb-live/src/venues/okx.rs:449-455` отдаёт
`MarketKind::LinearPerp` + `ContractSize::BasePerContract(0.01)` **и**
`SizeUnit::Contracts`, лестницу передаёт сырой. Собственный тест адаптера это
расхождение проговаривает:

```
okx.rs:876   assert_eq!(i.spec.size_unit, SizeUnit::Contracts);
okx.rs:880   assert_ne!(i.spec.size_unit, SizeUnit::implied_by(i.spec.size));
```

Адаптер знает, что две единицы расходятся, а сканер идёт за той, от которой
адаптер предупреждает. Охранный тест `arb-scan`
`a_requested_size_is_in_book_units_not_contracts` гоняет `contract_size` по
`["1", "0.01", "0.001", "0.0001"]` и требует, чтобы ответ не менялся — при
`size_unit`, прошитом в `Base` во всех четырёх. Охрана привинчена к
единственному случаю, который под вопросом и не был.

**Перевывод, точными целыми, до запуска кода.** Вход — записанные байты
`captured::INSTRUMENTS_BTC_USDT_SWAP`: `ctVal "0.01"`, `ctMult "1"`,
`lotSz "0.01"`, `tickSz "0.1"`. Цель 100 000 USDT, плечо 1, лучший аск 80 000.0,
лучший бид 79 999.0, вся заливка на первом уровне, поэтому VWAP = тач.

```
requested = 100000 / 80000 = 5/4 = 1.25            точно, REVENUE не срезает
lot       = max(0.001, 0.01) = 0.01                price_pair берёт более грубый
1.25 / 0.01 = 125                                  round_down_to_lot — тождество
```

OKX длинной ногой (`Opportunity::notional` — это нотионал длинной ноги):

```
НАПЕЧАТАНО  (5/4) * 80000                = 400000/4   = 100 000 USDT
ПРАВДА      (5/4) * (1/100) * 80000      = 400000/400 =   1 000 USDT
```

OKX короткой ногой, `79999 * 125 = 7 999 900 + 1 999 975 = 9 999 875`:

```
НАПЕЧАТАНО  (5/4) * 79999           = 9 999 875 / 100   = 99 998.75
ПРАВДА      (5/4) * (1/100) * 79999 = 9 999 875 / 10000 =    999.9875
```

Множитель — ровно `1 / ctVal = 100`. На Gate (`ctVal 0.0001`) это 10 000×, на
Binance, где контракт равен монете, ошибка численно исчезает и потому невидима.

**Почему это не ловится ничем на строке.** Две ошибки взаимно сокращаются внутри
`fit_to_budget`: заниженный запрос и завышенный отчёт дают
`realised = 1.25 * 80000 = 100 000 <= target`, проверка бюджета проходит с
первого проходa. `net_apr`, `fee_bps`, `slippage_bps` — отношения, посчитанные
согласованно внутри единиц лестницы, и выживают нетронутыми. Когда OKX короткая
нога, `Opportunity::notional` (нотионал Bybit) **верен**, а
`Opportunity::margin = 199 998.75` против правды `100 999.9875` — почти вдвое.
Ни одна колонка не противоречит другой.

**Строка ранжируется.** `blocked = []`, `is_rankable()` истинно, `paint_score`
ноль на обеих ногах — четвёртый тест это фиксирует и проходит. Он существует
чтобы закрыть единственный путь отхода: «строка всё равно заблокирована, значит
безвредна». Не заблокирована.

**Не хедж.** `price_pair` решает один `size` и отдаёт то же число в `price_leg`
для обеих ног. Один скаляр не может быть размером в двух разных единицах:

```
Bybit,  size_unit = Base:      1.25 книжных единиц = 1.25   BTC
OKX,    size_unit = Contracts: 1.25 книжных единиц = 0.0125 BTC
голая дельта = 1.2375 BTC = 1.2375 * 80000 = 99 000 USDT направленной позиции
```

`pair_check` эту пару разрешает: разные площадки, обе `LinearPerp`, база и котир
совпадают. Отказывает он только на том же инструменте, расхождении базы/котира,
линейном против инверсного и одноимённой площадке перп-перп.

**Владелец правки:** `ENG-SCAN` (`crates/arb-scan`). Я продуктовый код не
трогал.
