## 0. Одно неравенство, к которому сводится всё

Две тождества, обе точные, без округления:

`[fact, verified]` `SECONDS_PER_YEAR = 31_536_000`, интервал фандинга 8 ч = `28_800` с
(`arb-types`, все 14 фикстур с `[funding]`). Значит **1095 сеттлментов в году ровно**
(31 536 000 / 28 800 = 1095, целое). И **1095 / 365 = 3 ровно**.

> Следствие, на котором держится вся арифметика ниже: ставка `d` bp за сеттлмент — это
> `3d` bp в сутки, точно. Никакого округления в переводе нет.

Обозначения (все — базисные пункты нотионала):

| | что |
|---|---|
| `d` | расхождение фандинга, bp за сеттлмент 8 ч (сумма двух знаковых ног) |
| `C` | круговая издержка, bp — комиссии + проскальзывание + спред, четыре ноги |
| `b` | заём под короткую ногу спота, bp в сутки (`0` для перп↔перп) |
| `N` | сколько сеттлментов позиция **реально прожила** |
| `H` | горизонт удержания, сутки |

**Честная, дискретная форма — то, что действительно происходит:**

```
P&L за N сеттлментов, bp  =  N·d  −  C  −  (N/3)·b
```

Круг платится один раз, фандинг капает N раз, заём капает непрерывно. Отсюда:

```
окупается  ⟺  N  >  C / (d − b/3)          N* = ceil( C / (d − b/3) )
```

`[fact, verified]` При `b = 0` это ровно `ceil(C/d)` — то, что считает
`periods_to_breakeven` (`crates/arb-math/src/funding.rs`). Сверено: лучшая строка
`ceil(22.11 / 3.5) = 7`, движок печатает `BE 7`. MATCH.

**Годовая форма** (её печатает движок, амортизируя круг по горизонту):

```
net APR > 0  ⟺  3·d  >  C/H  +  b
```

### 0.1 Главное, что я нашёл: порог прибыльности — это захардкоженная константа горизонта

`[fact, verified]` Из годовой формы: `net > 0 ⟺ C/d < 3H`, то есть **`net > 0` ⟺
`N* ≤ 3H`**. Горизонт в движке — `Millis::from_secs(7 * 86_400)`,
`crates/arb-engine/src/lib.rs:123` и `crates/arb-engine/src/live.rs:105`; у `ScanConfig`
нет `Default`, значение приходит только оттуда. `3H = 21` сеттлмент.

Проверено эмпирически на всех 46 строках реплея — таблица сопряжённости:

| | `BE ≤ 21` | `BE > 21` |
|---|---|---|
| `net > 0` | **26** | 0 |
| `net ≤ 0` | 0 | **20** |

Максимальный `BE` среди положительных строк — ровно **21**. Минимальный среди
отрицательных — ровно **22**. Пустые клетки пусты не приблизительно.

> **Знак `NET APR` не несёт ни одного бита сверх колонки `BE`.** Он её пересказывает.
> А порог, отделяющий «зарабатывает» от «не зарабатывает», — это `H = 7 суток`,
> константа в движке, которую **ничто не проверяет против измеренной персистентности.**

Чувствительность, при неизменных рыночных данных до бита:

|---|---|---|

| 3 сут | 9 | 3 / 46 (7%) |
| 5 сут | 15 | 17 / 46 (37%) |
| **7 сут** | **21** | **26 / 46 (57%)** |

`[fact, verified]` Продукт **уже** предполагает семидневную персистентность. Молча,

персистентность «не измерена», а в том, что **вместо измерения подставлено число 7**,

### 0.3 Пятая издержка, которой нет в числе: спред

`[fact, verified]` `slippage_bps` (`crates/arb-math/src/execution.rs:167-180`) мерит
VWAP **от тача**, а не от мида: `Buy => vwap/touch − 1`, `Sell => 1 − vwap/touch`.
А `cost_bps = fee_bps + slippage_bps_total` (`crates/arb-scan/src/scan.rs:472`) —
и больше ничего. Значит переход через спред не оплачен нигде.

Он реален и не сокращается. За полный круг:

```
(ask_L − bid_S)  +  (ask_S − bid_L)  =  (ask_S − bid_S) + (ask_L − bid_L)  =  s_S + s_L
```

Межвенчурный базис сокращается между входом и выходом; **спред каждой площадки —
нет**, он платится по одному разу на каждой. Проверено напрямую на лучшей строке:
вход `68122 − 68122 = 0`, выход `68125.5 − 68118.5 = 7`, итого 7 единиц на миде
68122 = **1.0276 bp** — и это ровно `s_mexc + s_okx = 0.5138 + 0.5138`. Тождество
подтверждено.

| | |
|---|---|
| заявленный круг | 22.1100 bp |
| неучтённый спред | 1.0276 bp |
| **истинный круг** | **23.1376 bp** — занижение на **4.44%** |
| лишняя амортизация | 0.5358% APR |
| net 26.79% становится | **26.26%** |

По 28 парам BTC-перпов: минимум **0.9395** bp (bybit/gate), медиана **1.0276**,
максимум **1.7175** (htx/kucoin). На `d = 1.0` bp/8ч это сдвигает `BE` с 23 на
**24** сеттлмента, то есть с 7.67 на **8.00 суток** — за границу семидневного
горизонта. **Направление — благоприятное, то есть по §0 худшее.**

`[fact, verified]` Отдельно: выходная сторона книги **не обходится никогда**.
`slippage_bps_total = one_way + one_way` (`scan.rs:471`) — выход предполагается
зеркалом входа. Это допущение, а не измерение; при выходе в тонкую книгу оно
занижает. И третье: у мейкера этот член имеет **обратный знак** — стоящая заявка
исполняется по своей цене и спред не платит. Поэтому истинный рычаг
исполнения — не 2.75×, а **≥ 2.89×** (`23.1376 / 8`) и до **3.67×** в худшей паре
(`(24 + 1.7175) / 7`). Комиссия и спред — **один рычаг**, и код считает половину.

## 1. Условия, при которых стратегия зарабатывает

Каждое — неравенство с числом, каждое проверяемо.

**У1 — базовое.** `N_прожито · d > C + (N_прожито/3) · b`.
Эквивалентно `N_прожито > N* = ceil(C / (d − b/3))`.
Сегодня непроверяемо: `N_прожито` не измерено ничем, `C` неполон на спред, `b`
неизвестен всегда (см. Н5).

**У2 — персистентность, без единой вероятности.** Правильная величина —
не «шанс выжить», а накопленное расхождение:

```
E[ Σ d_i по прожитым сеттлментам ]  >  C
```

Это точно, не требует формы распределения и **не требует прогноза**. Оно требует
измерения: `mean_settled_rate · N` и есть `Σ d_i`. `[fact, verified]`
`crates/arb-math/src/persistence.rs` уже содержит ровно этот примитив
(`mean_settled_rate`, `realised_receipt_per_period`, `annualise_realised`).

Отсюда прикладной вид: **ранжировать по реализованному среднему, а не по текущей
печати.** Собственный тест модуля
(`realised_and_current_disagree_when_the_divergence_is_young`) даёт realised 21.9%
против current 109.5% APR — расхождение **5×**, и наверх сортируется льстивое.

Порог на частоту выживания, если он всё же нужен для чтения: при худшем допущении,
что умершее расхождение не платит ничего, `p > C / (3·H·d) ≈ N*/(3H)`.
`[assumption]` — держится на «умерло → ноль», что заведомо консервативно.
Читается так: лучшая строка (`N* = 7`, `H = 7`) требует `p > 1/3`; строка при
`d = 1` требует `p > 22/21 > 1` — **невозможно ни при какой вероятности**, что и
совпадает с таблицей §0.1.

**У3 — издержка.** При `b = 0` и `d > 0` окупается **любая** `C`, вопрос только —
когда. Проверяемые пороги на семидневном горизонте (`3H = 21`):
`C < 21·d`. При `d = 1` bp/8ч это `C < 21` bp — то есть **все 12 строк с
`C ∈ {30, 31, 32}` bp вне игры**, и все тейкерские пары BTC (20–24 bp) на грани.
При мейкерской конфигурации `C = 7…8` bp порог падает до `d > 0.381` bp/8ч.

**У4 — заём.** `b < 3d` строго, иначе не окупается никогда (Н4). И для строки,
дающей `net_apr` до заёма: `годовой заём < net_apr`, то есть
`b < net_apr/365` в сутки. Проверено против `OPEN.md` A1: `21.68% − 0.02%·365 =
14.38%`, `21.68% − 0.07%·365 = −3.87%`, безубыточный `b* = 21.68/365 = 0.0594%/сут`.
Обе цифры A1 воспроизведены точно.

**У5 — горизонт должен быть решением, а не константой.** `H ≤ E[N_прожито]/3`.
Сегодня `H = 7` задано в коде и не сверено ни с чем.

**У6 — ёмкость.** Процент на недостижимом размере — не деньги.
`[fact, verified]` Строки с htx упираются в **0.188 BTC** против запрошенных 1.468 —
≈12.8 тыс. нотионала вместо 100 тыс. Прибыльность надо мерить в деньгах за год,
а не в APR: 26.79% на 12.8 тыс. — это 3.4 тыс. в год, до вычета всего в Н8.

## 2. Что для этого надо измерить

### 2.1 Персистентность — `E[Σ d_i]`

**Кто:** `ENG-VENUE` (вход), `ENG-SCAN` (проводка), `ENG-BOOK` (вердикт),
`ENG-ENGINE` (колонка).

`[fact, verified]` Сейчас измерить нечем, и это структурно:
- `KNOWN_SECTIONS = ["instrument","funding","fees","book"]`
  (`crates/arb-venue/src/fixture.rs:310`) — секция `[history]` не «отсутствует», она
  **вызывает ошибку парсинга**. Ни одна фикстура не может принести историю.
- `LegInput::new` хардкодит `history: None` (`crates/arb-scan/src/leg.rs:90`);
  `with_carry_inputs` вызывается **только из тестов**. Оба движковых пути идут через
  `gather`. Значит `RATE_HISTORY_MISSING` стоит на **каждой** перп-ноге всегда.
- `arb-scan` читает с истории ровно одно: `h.is_empty()` (`scan.rs:512`).
- **Весь слой персистентности — мёртвый код.** Нулевые продакшен-потребители у
  `coverage`, `mean_settled_rate`, `realised_receipt_per_period`,
  `annualise_realised`, `sign_flips`, `periods_as_time`, `HistoryCoverage`,
  `RateHistory::current_sign_run`.
- **В `arb-detect` нет модуля персистентности вообще** (`clock, error, painted,
  sequence, staleness, trust`). Против `decisions/023` шаг 2, где вердикт с
  обоснованными порогами поручен именно ему.

**Сколько данных нужно.** Чтобы назвать частоту выживания с разрешением `1/K`,
нужно `K` **неперекрывающихся** окон по `N*` сеттлментов, то есть `K·N*/3` суток:

| `N*` | окно | `K=5` | `K=10` (10%) | `K=20` (5%) |
|---|---|---|---|---|
| 8 (мейкер) | 2.67 сут | 13.3 сут | **26.7 сут** | 53.3 сут |
| 21 | 7.00 сут | 35.0 сут | 70.0 сут | 140.0 сут |
| 22 | 7.33 сут | 36.7 сут | **73.3 сут** | 146.7 сут |
| 24 (со спредом) | 8.00 сут | 40.0 сут | 80.0 сут | 160.0 сут |

Год = 1095 сеттлментов = 49 окон по 22 или 136 окон по 8. Перекрывающиеся окна
**завышают** объём выборки и запрещены.

Требование, которое легко потерять: истории двух ног должны быть **выровнены по
общей сетке сеттлментов**, потому что выжить должно *расхождение*, а не ставка
каждой ноги по отдельности. `[fact, verified]` `gate-btcusdt-perp.fix:39` несёт
`interval_source = assumed` — у одной из восьми площадок сетка не подтверждена.

**Пороги, которые я предлагаю, все честные — ни один не возвращает вероятность:**
1. `periods_spanned ≥ periods_needed` (`HistoryCoverage::covers`) — **предусловие
   разрешимости вопроса, не ответ**; так и написано в модуле. Не покрыто → блок, не флаг.
2. `current_sign_run ≥ N*` — расхождение держит знак хотя бы столько, сколько нужно.
3. Частота переворотов `sign_flips ≤ (settlements − 1)/N*` — при `N* = 22` это
   ≤ 12 переворотов за 90 суток.
4. **Сильнейший:** ранжировать по `annualise_realised(mean_settled_rate(...))`, а
   текущую печать показывать рядом. Требование `3·d̄ > C/H + b`.

Заметка `[fact, verified]`: `decisions/025` прав, и я его не обхожу — прогноз из
девяти точек был бы ровно той нечестностью, ради устранения которой существует
проект. **Поэтому я не даю вероятность.** Я даю: сколько нужно данных (таблица
выше), какой порог (четыре пункта выше) и какую величину мерить (`E[Σ d_i]`).

### 2.2 Заём под короткую ногу спота — `b`

**Кто:** `ENG-VENUE` (секция `[borrow]` — сегодня тоже структурно невозможна,
`KNOWN_SECTIONS`), `ENG-SCAN` (`gather` хардкодит `borrow: None`), `LEAD`
(`BorrowSnapshot` заморожен).

`[fact, verified]` Механика верна и полна: `annualise_borrow`,
`net_apr_after_borrow`, отказ от отрицательной ставки, `RoundMode::COST` везде,
и явное разделение «круг разовый / заём непрерывный» — подача заёма через
амортизирующий путь льстила бы в **1095×** на 8-часовом удержании.

**Но ветка `Some(snap)` в продакшене недостижима** (`scan.rs:497`): обратный кэрри
никогда не оценивается, только блокируется. Ровно **2 строки из 46** несут
`BORROW_UNKNOWN`.

**Порог, резкая форма:** заём убивает обратный кэрри при `b ≥ 3d` — **на любом
горизонте, и никакой тариф не спасает**, потому что комиссия меняет *когда*, а не
*окупится ли вообще**:

| заём | bp/сут | нужно `d` > | против фикстур (max 3.5, медиана 1.2) |
|---|---|---|---|
| 10.0% APR | 2.7397 | 0.9132 bp/8ч | проходит 18 пар из 28 |
| 20.0% APR | 5.4795 | 1.8265 bp/8ч | проходит 7 из 28 |
| **50.0% APR** | **13.6986** | **4.5662 bp/8ч** | **не проходит ни одна** |
| 87.6% APR | 24.0000 | 8.0000 bp/8ч | не проходит ни одна |

Обратно: `d = 1.0` bp/8ч → смерть при `b = 3.00` bp/сут = **10.95% APR**;
`d = 1.2` → 13.14% APR; `d = 3.5` → 38.32% APR.

**Мерить надо не только ставку:** интервал начисления (`BorrowInterval` — та же
цифра как суточная и как часовая различается в **24×**, и тест это пиннит),
доступность заёма, изменчивость ставки под стрессом и берётся ли плата за
открытие. Ни одно из четырёх не покрыто (`OPEN.md` A1).

## 3. При каких условиях НЕ зарабатывает

Этот раздел важнее первого. Прямо.

**Н1. Сегодня — не зарабатывает, и продукт это говорит честно.**

выдуманных байтах, и §B `OPEN.md` уже говорит это прямо.

**Н2. Не зарабатывает на типичном расхождении 1 bp/8ч ни при какой тейкерской
издержке на семидневном горизонте.** `C = 22` bp → `N* = 22` сеттлмента = 7.33 сут.

Работает только уход в мейкера: `C = 8` bp → `N* = 8` = 2.67 сут.
**Расхождение 1 bp/8ч и тейкерское исполнение несовместимы.** И это тот самый
типичный случай, из которого стоит исходить: медиана по 28 парам фикстур — 1.2 bp,
и только **1 пара из 28** даёт 3.5 bp.

**Н3. Не зарабатывает, если удержание короче `N*/3` суток.** 20 строк из 46 уже
в этом состоянии. И знак — целиком функция константы `H` (§0.1): на трёх сутках
положительных строк остаётся 3 из 46.

**Н4. Обратный кэрри не окупается НИКОГДА при `b ≥ 3d`** — ни на каком горизонте,

`d > 4.5662` bp/8ч; максимум по всему набору фикстур — 3.5 bp, медиана 1.2.

**Н7. Не зарабатывает, если ранжировать по напечатанному числу — а сортировка
